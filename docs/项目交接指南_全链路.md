# Operation Metrics Skill：快速上手与全链路交接指南

> 适用目录：`E:\Operation-Metrics-Skill`  
> 目标：帮助交接人员理解“数据如何变成报告”，知道每一步改哪里、输入输出是什么，以及哪些地方不能随意改。

## 1. 先看懂整体链路

```text
Raw Data
  -> Preflight / 字段可用性检查
  -> Field Mapping / 源列名映射为标准字段
  -> Normalize + Aggregate / 清洗并按粒度汇总
  -> Metrics / 计算确定性指标
  -> Rules / 执行规则
  -> Rule Result / 输出结构化事实与证据
  -> Prompt + Report / 依据事实生成五屏报告
  -> Semantic Blocks / 把报告拆成可渲染结构
  -> DOCX Renderer / 生成可编辑 Word
  -> QA / 内容、结构、OOXML、血缘检查
```

核心原则：数字必须来自已验证原始数据和确定性指标；经营判断必须来自正式 Rule Result；缺数据写“数据不足/待确认”，不能猜测或把未命中写成“业务健康”。

## 2. 目录地图

| 目录/文件 | 作用 | 什么时候改 |
|---|---|---|
| `raw_data/` | 原始 Excel 数据，按分卷保存 | 只替换/新增经过确认的原始数据，不在此处改口径 |
| `reference/` | 指标规则总表及参考数据 | 更新业务口径或参考样本时 |
| `src/field_mapping.py` | 源 Excel 列名到标准字段的映射 | Excel 列名变化、增加字段 |
| `src/aggregate_metrics.py` | 读取源表、校验、标准化、调用指标层 | 输入格式或编排方式变化 |
| `src/metrics/` | 月份完整性、渠道/品类聚合和指标计算 | 修改聚合粒度或指标定义 |
| `src/rules/` | S1/S2/S3 规则评价 | 增加规则、修改规则实现（需同步合同和测试） |
| `src/rule_result.py`、`docs/rule_result.schema.json` | Rule Result 数据结构、校验、CSV/JSON 输出 | 协议字段变化 |
| `config/` | 字段别名、指标/规则/报告依赖声明 | 声明新增字段、规则覆盖或屏幕依赖 |
| `prompts/` | 报告各模块 Prompt 和共享约束 | 调整语言、结构或表达边界 |
| `workflows/`、`scripts/workflow_runner.py` | 全链路状态机和阶段编排 | 增加阶段、恢复流程或 QA |
| `semantic_blocks.json`、`assets/` | 报告结构块及嵌入资源 | 改报告结构或资源映射 |
| `scripts/*docx*` | Semantic Blocks 与 DOCX 互转/渲染 | 改 Word 格式、表格、图片资源处理 |
| `outputs/` | 已生成的指标、规则、报告和 QA 产物 | 可清理重建，不作为源数据 |
| `tests/` | 单元测试和工作流测试 | 每次口径或接口变化都应补测 |

## 3. 各阶段原理、接口和改进方向

下面每一节都先用通俗的话说明“这一步到底在干什么”，再补充代码接口。理解业务目的比先记住文件名更重要。

### 3.1 Raw Data：原始数据

这里的 Excel 只是当前用于验证整条链路的一种输入样子，不代表以后只能接受这一种表。后续会接入各种各样的 Excel，核心要求不是文件长得完全一样，而是能够通过字段识别或字段映射，让系统知道哪一列是日期、品类、渠道、成本、订单等。原始文件本身尽量不改，适配工作放到识别和映射层完成。

技术上：原始数据层保留业务系统导出的事实，不在原始文件中人工修正。当前主要输入是 Excel，默认工作表为 `数据源`。

```python
raw = load_source(Path("raw_data/某份数据.xlsx"), sheet_name="数据源")
```

接口：输入是 `xlsx + sheet_name`；关键字段由 `src/field_mapping.py` 声明。当前主分析粒度是“自然月 × 三级渠道”或“自然月 × 所属品类”。

可修改/优化：

- 增加新的分卷或新版本 Excel，但要记录来源、日期范围、文件哈希。
- 以后适配新 Excel 时，优先增加“可识别字段”的配置或映射规则，让不同名称的列归一到同一个标准字段。例如“获客成本”“投放成本”“获客总成本”都可以识别为 `cost`，但必须确认它们业务含义一致。
- 需要支持 CSV/多个工作表时，扩展加载器，并按扩展名选择读取器。
- 大文件应使用只读/流式读取做检查，避免用完整 `pandas.read_excel` 扫描超大文件。
- 不要把“没有数据”默认为 0；缺列、非法数值、关键维度空值应显式失败。

### 3.2 Preflight：执行前检查

这一步像“开工前验货”。先判断这份表能不能用、能做哪些分析、哪些分析做不了，避免数据不完整却生成一份看起来很正式的报告。

技术上：先回答“这批数据能不能支持哪些分析”，再执行。检查日期范围、字段存在性、字段类型、月份完整性、数据粒度和规则覆盖。

接口：主要由 `src/preflight.py`、`workflows/preflight.md`、`schemas/preflight.schema.json` 定义；输出通常是 JSON 预检结果和执行计划。

可修改/优化：

- 增加重复行、异常日期、负金额、跨月缺口等检查。
- 把“可执行/不可执行”的规则清单输出得更明确。
- 任何新增检查都应区分阻断错误、警告和信息，避免把可处理警告误判为失败。

注意：完整工作流要求 Preflight 后进入审批门；审批不是计算步骤，而是防止错误输入直接生成正式报告的控制点。

### 3.3 Field Mapping：字段映射

不同部门、不同系统导出的 Excel，列名经常不一样，但“成本”“渠道”“首单营收”这些意思可能是一样的。字段映射就是做一个翻译表，把各种写法翻译成系统统一认识的名字。以后接新 Excel，主要就是补充这种识别/翻译关系。

技术上：把易变的中文 Excel 列名转换为稳定的标准字段。指标层只使用 `cost`、`channel` 等标准字段，不直接依赖源列名。

```python
FIELD_MAP["cost"] = FieldSpec("获客总成本", "money", "渠道获客投入成本")
raw = raw.rename(columns=source_to_standard())
```

接口：

- 主要接口：`FIELD_MAP`、`FieldSpec(source, type, description)`。
- `source_columns()`：告诉读取器需要哪些源列。
- `source_to_standard()`：执行重命名。
- `validate_source_columns()`：缺列即失败。
- `config/field_aliases.yaml`：预留别名声明，但当前主加载逻辑以 Python 的 `FIELD_MAP` 为准。

增加字段的步骤：在 `FIELD_MAP` 增加标准字段；如需汇总则加入 `ADDITIVE_FIELDS`；在指标依赖配置、指标层、测试和文档中同步声明。新增字段不能只改配置而不改读取与计算代码。

可修改/优化：

- 把别名解析真正接入加载器，并在多个候选列同时存在时报冲突。
- 为字段增加单位、是否必填、是否可聚合、来源版本等元数据。
- 将 `FIELD_MAP` 外置为严格校验的 YAML/JSON，但要保留版本和回归测试。

### 3.4 Normalize + Aggregate：标准化和聚合

原始表通常是一行一条明细，但报告要看“每个月每个渠道”或“每个月每个品类”。这一步就是把明细整理成报告需要的统计层级。比如成本和订单数可以加总，但转化率不能把每行的转化率直接平均，而要用加总后的订单数除以加总后的线索数。

技术上：先将日期、维度和数值转为标准类型，再对可加总字段求和；比率必须使用聚合后的分子和分母重算，不能平均明细比率。

```python
grouped = raw.groupby(["month", "channel"], as_index=False)[list(ADDITIVE_FIELDS)].sum()
```

当前实现：`src/aggregate_metrics.py` 负责加载和基础标准化；`src/metrics/channel.py` 按 `month + channel` 聚合；`src/metrics/category.py` 按 `month + category` 聚合；`month_coverage()` 标记完整自然月。

接口：

- 渠道主键：`["month", "channel"]`。
- 品类主键：`["month", "category"]`。
- 加总字段：`ADDITIVE_FIELDS`。
- 月份完整性：`is_complete_month`。
- CLI：`aggregate_metrics.py input output --category-output ... --sheet-name ...`。

修改聚合粒度：修改对应 `groupby([...])`，同时修改唯一键、指标依赖、规则所需连续月份、输出字段、测试和报告引用。比如改成“月 × 渠道 × 账户”，不能只在 groupby 中加一列，否则不同模块可能出现键不一致。

可修改/优化：

- 将粒度定义集中到配置，并在运行时输出实际 grain/key。
- 增加来源行数、聚合前后金额校验和粒度唯一性检查。
- 对多账户/多部门数据明确是“合并”还是“分组”，禁止默认去重。
- 当前 `first_order_users_proxy` 是首单订单数代理，不是真实用户数；不能改名后造成语义升级。

### 3.5 Metrics：确定性指标

这一步负责把“成本、订单、营收、线索”变成大家常用的数字，比如 CAC、ROI、转化率。它只负责按公式算数，不负责判断“好不好”或“为什么会这样”；这样同一份数据每次重跑都能得到同样的结果。

技术上：指标是可复现的纯计算层，不负责写经营结论。当前包括 CAC、CAC 率、首单转化率、渠道 ROI、重复线索率、品类营收占比等。

```python
grouped["cac"] = safe_divide(grouped["cost"], grouped["first_order_orders"])
grouped["channel_roi"] = safe_divide(grouped["first_order_revenue"], grouped["cost"])
```

接口：`src/metrics/common.py` 提供 `safe_divide()` 和月份完整性；渠道指标在 `build_channel_metrics()`；品类指标在 `build_category_metrics()`。

可修改/优化：

- 新指标按“名称、公式、单位、分子、分母、空值规则、来源”完整登记。
- 比率统一用聚合后的分子/分母计算；分母为 0 应保留空值或不可执行状态。
- 增加指标元数据清单，避免 `cac` 与 `cac_rate`、重复线索率与复购率混用。
- 每个指标补一个边界测试：0 分母、空数据、负值、缺月、单月数据。

### 3.6 Rules：规则引擎

指标只是数字，规则才是“如果满足某个条件，就发出一个信号”。例如连续三个月 CAC 率上升，就命中一个风险规则。规则不是人工拍脑袋，也不是让模型自由发挥，而是把已经确认的业务判断写成可以重复执行的条件。

技术上：规则只判断预先定义的条件，并生成命中和未命中记录。跨月规则只使用连续完整自然月；规则本身不猜原因。

```python
hit = current_cac_rate > previous_cac_rate + 0.05
```

当前规则：S1 品类集中度/分散/下行/增长切换/涨跌分化/系统性下跌；S2 CAC 连续上升和环比跳升；S3 低 ROI 消耗占比。实现位于 `src/rules/`。

接口：每条结果包含 `module`、`rule_id`、`rule_name`、`hit`、`dimension`、`period`、`metrics`、`threshold`、`evidence`。依赖和最小月份声明在 `config/rule_dependencies.yaml`。

增加规则的步骤：先确定业务定义和证据边界；登记规则依赖与最小月份；在对应模块实现；补充 Rule Result Schema/单测；验证唯一键、NaN/inf、连续月份和证据文本；最后再让 Prompt 消费该规则。

可修改/优化：

- 将阈值、窗口长度和比较符号参数化，但必须版本化，避免历史结果不可解释。
- 统一输出 `NOT_EXECUTABLE` 或缺口信息，而不是把输入不足当成 `hit=false`。
- 给每条规则增加实现版本、输入快照哈希和证据来源引用。

### 3.7 Rule Result：事实协议

这是数据计算和报告写作之间的“交接单”。它把规则是否命中、涉及哪个渠道/品类、时间范围、具体数字和证据都写清楚，后面的 Prompt 只能根据这张交接单写报告，不能自己重新算数或编原因。

技术上：Rule Result 是数据与语言模型之间的边界层。它同时保留命中和未命中，模型只能引用其中的事实和证据。

```python
payload = json.loads(Path("outputs/engine/rule_results.json").read_text())
hit_results = [item for item in payload["results"] if item["hit"] is True]
```

接口：`src/rule_result.py` 负责对象、唯一键、JSON/CSV 序列化和校验；正式 Schema 是 `docs/rule_result.schema.json`。

可修改/优化：

- 协议新增字段要同步 dataclass、Schema、序列化、测试和下游 Prompt。
- 保持 `rule_id + dimension + period` 唯一。
- 保留数值型 `metrics` 与可引用的 `evidence`，不要让报告层重新计算。
- 变更 `schema_version`，并保留旧版本兼容策略。

### 3.8 Prompt 与 Report：从事实到五屏报告

前面已经把数据和规则算好了，这一步相当于“把结果讲给业务人员听”。Prompt 可以调整说话方式、标题和组织顺序，但不能为了让文章更完整而补数字、猜原因或扩大规则覆盖范围。

技术上：Prompt 负责表达，不负责创造事实。报告保持五屏结构：S1 品类、S2 渠道成本、S3 投放有效性、S4 覆盖边界、S5 总结。正式数字来自指标和 Rule Result，缺口要显式说明。

接口：`prompts/shared.md` 是共同约束，其他文件按模块组织；`references/report-contract.md` 和 `references/evidence-policy.md` 是边界合同；`scripts/assemble_report.py`、`scripts/build_vol01_report.py` 负责组装特定报告产物。

可修改/优化：

- 可改语气、段落模板、标题和展示顺序，但不能改事实边界。
- 新增一个报告模块前，先定义它消费哪些 Rule Result 和指标。
- 在 Prompt 中明确“hit=false 不等于健康”“未检查不等于通过”。
- 将 Prompt 版本写入报告元数据，便于回溯同一事实为何产生不同表达。

### 3.9 Semantic Blocks：内容与格式解耦

不要把报告正文和 Word 排版搅在一起。这里先把内容拆成“标题、正文、表格、图片”等积木，之后想换字体、间距或版式，只改渲染方式，不改已经确认的文字和数字。

技术上：把报告拆成标题、正文、列表、表格、图片/资源等语义块。上游文本、顺序和语义角色是内容契约；下游只负责排版和资源落位。

```json
{"type": "finding_heading", "text": "渠道获客成本连续上升"}
```

接口：`semantic_blocks.json`；转换脚本为 `scripts/docx_to_semantic_blocks.py` 和 `scripts/semantic_blocks_to_docx.py`；资源索引是 `assets/resource_map.json`。

可修改/优化：

- 增加新的 block type 时，同时更新 Schema/转换器/回读检查。
- 需要改文案时改上游内容块；需要改字号、间距、表格样式时改 Renderer，不要互相污染。
- 资源路径必须可定位，嵌入 Excel 和预览图要做数量、顺序和存在性检查。

### 3.10 DOCX：可编辑交付格式

最后要交付的是可以继续编辑的 Word，不是几张报告截图。这个阶段主要解决“怎么排得好看、怎么保证表格和文字还能编辑”，不应该偷偷改变上游内容。

技术上：用 Word 原生段落和表格生成可编辑文档，不把整页截图当成报告。当前字体规范：正文/表格 Arial 11 磅，标题 26 磅，一级/二级/三级标题 18/16/15 磅。

```powershell
python scripts\semantic_blocks_to_docx.py --input-blocks semantic_blocks.json --output outputs\示例报告.docx
```

接口：`scripts/semantic_blocks_to_docx.py` 的输入是 blocks JSON 或 DOCX，输出是 DOCX 和同名 QA JSON。

可修改/优化：

- 改字体、边距、表格宽度、分页规则时集中修改 Renderer 样式常量。
- 任何样式修改都要检查保存后的 OOXML，不仅看内存对象。
- 需要视觉验收时必须实际渲染页面；没有 `soffice`/图片渲染工具时，只能声明结构 QA 已完成，不能声称视觉 QA 通过。

### 3.11 QA 与交付

这一步不是“程序没报错就算完成”，而是要确认从哪份 Excel 出发，最后确实生成了正确的指标、规则和 Word。还要区分代码测试通过、文件结构正确和页面视觉效果通过，这三件事不是一回事。

技术上：QA 验证“文件存在、协议正确、内容保真、格式可解析、血缘闭合”，不是只看命令是否退出成功。

接口：`tests/`、`scripts/validate_stage.py`、`outputs/runtime/*qa*.json`、`artifact_lineage_qa.json`、`run_manifest.json`。

建议验收顺序：

1. 运行单元测试：`pytest -q`。
2. 检查 Preflight、指标 CSV、Rule Result JSON/CSV。
3. 检查 Semantic Blocks 内容、顺序和资源。
4. 检查 DOCX QA、OOXML QA；有条件再做页面图片视觉 QA。
5. 核对 `run_id`、输入绝对路径、SHA-256 和各阶段输出，确认 Raw Input → DOCX 血缘闭合。

## 4. 常见改动的最小影响范围

| 需求 | 至少要改/检查 |
|---|---|
| Excel 改列名 | `FIELD_MAP`、别名配置、字段测试、Preflight |
| 增加原始字段 | `FIELD_MAP`、加总字段或指标依赖、读取、指标、测试、合同 |
| 改聚合粒度 | channel/category metrics、主键、规则连续月份、配置、报告、测试 |
| 增加指标 | 指标实现、公式/单位元数据、依赖、边界测试、报告输入 |
| 增加规则 | 业务合同、规则依赖、实现、Schema/Rule Result、测试、Prompt |
| 改报告文案 | `prompts/` 或上游 blocks；不改事实数据 |
| 改 Word 格式 | Renderer 样式/资源处理；保留 blocks 文本；重跑 QA |
| 换数据重跑 | 新输入路径、Preflight、全链路输出和 manifest；不要直接覆盖原始数据 |

## 5. 当前已知注意事项

- 当前目录没有发现 `.env`、`.env.local` 等环境文件；本项目当前主要通过本地 Python 运行时和代码参数工作，不要把个人密钥写入仓库。
- `.venv/` 是本机环境，不适合直接交接；同事应依据依赖重新建立环境。
- `outputs/` 中有历史产物，使用前确认对应的输入文件、运行时间和版本，不要把历史产物当成当前结果。
- `_input_vol03.xlsx` 和 `raw_data/` 可能较大，复制/解压需要足够磁盘空间。
- 规则结果的未命中只表示条件未触发；S4 因缺少竞品/市场份额真实数据不应生成正式规则结论。
